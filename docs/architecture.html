PR Review Agent Architecture

A daemon that polls configured repositories, reviews newly-opened pull requests with a per-repo role, and posts findings as inline comments — driving a reviewer that cannot write files, open a shell, or reach the network.

01The system at a glance

Everything is driven by one timer. Each tick, the poller asks GitHub’s Search API which pull requests match, and hands the numbers to an orchestrator that walks a single PR from clone to posted review. Reads fan out across three GitHub endpoints; writes go through exactly one module.

02What one cycle decides

Each cycle runs two passes per repository. The auto pass finds PRs matching the repo’s raw GitHub filter string; the manual pass finds PRs where someone commented the trigger phrase. They converge on the same reviewer, but they pass through different gates — a human asking for a second opinion should not be refused because the PR is a draft, or because an earlier attempt failed.

03The containment boundary

The reviewer runs with its working directory set to a checkout of code written by whoever opened the pull request. That is the whole security problem: attacker-controlled content, an agent with tools, and a host holding a GitHub token.

Three findings during construction shaped this boundary. A prefix allow-list on git turned out to be bypassable — git diff --output=<file> writes anywhere — so shell access was removed entirely rather than filtered. A PR that committed its own .claude/settings.json could run hooks on the host, which a working proof-of-concept demonstrated and the current flags demonstrably stop. And PR-derived text is wrapped in XML tags with closing sequences escaped, so a comment saying “ignore your instructions” reads as data.

05Invariants worth keeping

  • One write path. Only post-review.ts writes to GitHub, and it always posts event: "COMMENT". The agent cannot approve or request changes because nothing in the system can.
  • State is recorded after the post, not before. A failed post is retried next cycle instead of being silently marked done — except on the manual path, where the trigger id is recorded first so a single comment cannot start an unbounded retry.
  • The token never reaches the agent. The child process gets an explicit environment allow-list, and every finding is passed through redaction before it is posted.
  • PR content is data, never instruction. Titles, bodies, diffs, and prior reviews are XML-tagged, with closing sequences escaped so they cannot terminate their own block.
  • Manual review always wins over automation. It ignores the filter, prior reviews, the draft skip, and the failure cap — a person asking for another pass gets one.

06Running it

Commands

# continuous, the normal mode
node dist/index.js run

# one cycle, then exit
node dist/index.js poll-once

# force a pass on one PR
node dist/index.js review \
  --repo owner/name --pr 42

Deployment

A Dockerfile and docker-compose.yml ship with the project; the image installs git because the harness clones, and deliberately omits gh because the agent has no shell to call it from. For Windows, docs/windows-service.md covers running it under NSSM. Secrets come from a gitignored .env: a personal access token and an Anthropic API key.

07Known limits

  • The Docker build has never been run. Docker was not installed on the build machine, so the image is unverified.
  • The first run reviews every matching open PR. Forty open PRs means forty paid runs and forty public comments. Add created:>=YYYY-MM-DD to the filter for the first cycle.
  • Exactly one instance per state file. There is no locking; two daemons sharing a state file will double-post.
  • The search endpoint is deprecated in the pinned client version. Both query shapes should be checked against live GitHub before relying on them.
  • A failed manual trigger is not retried. The trigger comment is consumed whether or not the review succeeded; comment again to ask for another pass.
